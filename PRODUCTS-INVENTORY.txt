# Products and Inventory (Divit, Phase 1)

For the updated Phase 2 behavior and current shared-login integration, see
[PHASE2-PRODUCTS.txt](PHASE2-PRODUCTS.txt). The remainder documents the original Phase 1 module.

The module uses the team's Java 25, Spring Boot 3.5.16, Maven, MySQL, JPA,
Thymeleaf and Bootstrap setup. Entity names are unchanged: `Product`, `Store`,
and `Inventory`. Classes follow the existing `com.soss` layer packages.

## Pages

| Route | Purpose |
| --- | --- |
| `/` | Redirect to the catalogue |
| `/products` | Catalogue, store selection and filters |
| `/search` | Name/description search, aisle, price and stock filters |
| `/products/{id}?storeId={id}` | Product details and branch availability |
| `/inventory` | Staff/admin inventory management |
| `/inventory/new?storeId={id}` | Add a product |
| `/inventory/{id}/edit?storeId={id}` | Edit shared details and selected branch stock |
| `/inventory/login` | Staff sign-in |

The supplied `index.html`, `search.html`, `inventory.html` and `styles.css` form
the basis of the module templates and styling. Templates are under
`templates/products`; static assets are grouped under `css/products` plus
`js/products.js`. Product cards link to product details. Cart actions must be
connected by the cart module once its endpoint and request contract are agreed.

The application starts with an empty catalogue. A staff member adds a real store
through Inventory, then products. Adding a store creates zero-stock Inventory rows
for existing products. Adding a product creates a row for every store; only the
selected store receives the entered stock. Product name, description, price, aisle,
icon and visibility are shared across branches. Stock is specific to each branch.
Zero means out of stock; 1-10 means low stock. Hiding a product preserves its IDs
and references while removing it from customer catalogue/detail access.

## Authentication integration

This branch adds Spring Security because inventory writes require STAFF or ADMIN.
Its filter chain only covers `/inventory` and `/inventory/**`, with CSRF protection.
Other module routes are left for their owning modules' security configuration.
Use authorities `ROLE_STAFF` and `ROLE_ADMIN` from the shared `User` login module.
The inventory controller also uses method authorization.

An optional local login lets Divit test before authentication is merged:

```text
INVENTORY_LOCALLOGIN_ENABLED=true
INVENTORY_LOCALLOGIN_PASSWORD=<a private password of at least 12 characters>
```

The local username is `divit` with role STAFF. These settings are environment
variables, never committed credentials. Disable this optional login when the
team's UserDetailsService is integrated. Do not create a second User entity.
The provided login template is scoped to inventory; it does not replace the
authentication teammate's login/register/profile pages.

## Contracts to coordinate

- All entity IDs are generated `Long` values.
- `Product`: id, version, name, category, description, price (`BigDecimal`), icon,
  active. SQL table: `product`.
- `Store`: id, name. SQL table: `store`.
- `Inventory`: id, version, Store, Product, quantity. SQL table: `inventory`, with
  a unique `(store_id, product_id)` pair.
- `CatalogueService.detail(productId, storeId, false)` loads customer-visible
  product and stock data within a read transaction.
- `CatalogueService.deductStock(productId, storeId, quantity)` locks the stock row
  and rejects nonpositive amounts, hidden products, and insufficient stock.
  The payment/order module should call it inside its successful-payment database
  transaction. The caller must ensure the payment/order is processed only once;
  this method is not an idempotency boundary. For multiple products, acquire locks
  in a consistent product-ID order. A failed payment must never call deduction.
- Editing uses version fields so a stale form cannot overwrite a newer change.
- There is no payment endpoint, cart implementation, Order entity, or sample-data
  initializer in this module.

Coordinate the POM's security dependency, homepage redirect, shared entity fields,
and authentication filter ordering before merging with the team.

## Verification

Run `mvn verify` with JDK 25. Seven integration tests cover rendered pages,
filters, branch stock, stock deduction, stale updates, hidden products, staff/admin
authorization, CSRF, validation, persistence, and empty/not-found states. H2 is a
test-only dependency. Normal application startup still requires MySQL and the
team's DB_USERNAME and DB_PASSWORD environment variables.

Browser verification additionally exercises local staff sign-in, store/product
creation, stock editing, search, product detail and mobile navigation. Temporary
browser verification records are removed from the local database afterward.
